§ 01

Executive Read

Functional equivalence is demonstrated, not asserted: All testcases passed against the live screen, with zero critical or high-severity failures and no data-loss, data-corruption or unauthorized-access defect. The blockers to calling this production-ready are not functional — they are one critical transport-security gap (no TLS anywhere in the built target) and one unverified test suite. Both are configuration and build-gate work, not redesign.

§ 03

The agent sequence, phase by phase

Phases run in order and each one is fronted by its own command. Where two agents sit in the same phase they either run in parallel (independent reads of the same source) or strictly sequentially (each consumes the previous one's artifact). The order is not a convention — it is enforced by what each agent is permitted to read.

Stage A Understand the legacy estate — read-only, no interpretation of intent yet
01

Discovery /01-Discovery

discovery-agent

Parses the CICS CSD to map every transaction to its program, then walks the COBOL to build a cross-reference of what each program actually touches — called programs, maps, copybooks, VSAM files, DB2 tables and TS queues, with the CRUD verb for each. Finally it reads the BMS copybooks to extract field-level screen metadata: name, length, position, attributes, initial values.

ProducesTransVsPgm.md · CicsXref.md · Screen-metadata.md
02

Discovery cross-check /02-ReviewStage1

review-gate1

An adversarial re-read: every claim in the three discovery documents is checked back against the actual source files, hunting for components missing from the docs, documented components missing from the repo, and inconsistent mappings. On MG-01 both the transaction map and the screen metadata came back clean; the only findings were informational — an undocumented batch program with no CICS verbs, and copybook members referenced but not supplied.

ProducesReviewGate1.md
Gate 1 · Human The pipeline stops. Nothing proceeds to grouping until a person approves the discovery review — this is the checkpoint where "we have understood the estate" is a human judgment, not a model's.
Stage B Decompose into shippable units and give each one a business meaning
03

Move-group clustering /03-MoveGroup

Create-Tran-group

Clusters transactions and programs into move groups — the migration unit — by shared mapset or by common branching from a user menu. This is the step that turns an estate into a delivery backlog: CTLI and CTTU share the Transaction Type table and cross-link by PF-key, so they became MG-01 and ship together.

ProducesMoveGroup.md
04

Business & behaviour capture /04-CreateBDDBSTS

Tran-Group-BSTSTran-Group-BDD

Two agents run in parallel over the same source. BSTS writes the business and technical summary — what the screen is for, every rule, cited to the COBOL paragraph that implements it. BDD writes pure Gherkin scenarios for the same behaviour: validations, exact legacy error text, edge cases, error handling. Together they become the specification of record; downstream agents never re-read COBOL.

ProducesMG-01-…-BSTS.md · MG-01-…-BDD.md
05

Database provisioning /05-CreateDB

Setup-DB

Mines the group's DB2 CRUD footprint against the DCL, DDL and control members, documents the resulting PostgreSQL schema, then connects to the live database over MCP and provisions it — tables, indexes, constraints. The schema is owned by this phase alone; the service is configured never to emit DDL.

ProducesMG-01-…-DB-Details.md + live PostgreSQL objects
Stage C Design the target, then have it reviewed before a line is trusted
06

Target build specification /06-TargetBuild

Refactor-UI-SpecRefactor-Backend-SpecRefactor-Reconcile-Spec

Strictly sequential, and this is the heart of the pipeline. UI-Spec rationalizes the 3270 map into a modern screen, strips every legacy identifier from the target design, and enforces WCAG 2.2 AA and GDPR at the presentation layer. Backend-Spec then designs services, endpoints and data access against that UI, carrying every business rule and error path across, and mandating OWASP, TLS 1.3 and OAuth 2.0 + JWT. Reconcile-Spec stitches the two — every field to its endpoint, every action to its rule — and emits the target architecture and a run guide.

ProducesMG-01-UI-Spec.md · MG-01-Backend-Spec.md · MG-01-reconcile-Spec.md · MG-01.Architecture.md
07

Build-readiness review /07-ReviewGate2

Review-Gate2

Re-derives ground truth independently from the legacy source, the BSTS/BDD and the stack config, then audits all four Phase-6 artifacts against it — checking field lengths and screen positions against the BMS, and every referenced design token against the style sheet. Findings are ranked Critical, Good-to-Have and Advanced, with architecture recommendations separated out. It edits nothing; applying a finding means re-running the owning spec agent.

ProducesMG-01-ReviewGate2.md — verdict: Ready with fixes (1 critical, 7 good-to-have, 5 advanced, 5 architecture)
Gate 2 · Human The second stop. A person decides which review findings are implemented before the target build is trusted — the point at which cost, risk and scope are traded off by an accountable human.
Stage D Prove equivalence against the running screen, then harden it
08

Functional-equivalence testing /08-TestTarget

Test-Writer-RefactorTest-Runner-RefactorTest-Bug-Fix

The Writer derives test cases from the BSTS, BDD and DB details only — never from the target code, so the tests cannot inherit the implementation's assumptions. The Runner executes them against the live stack: a real browser driving the SPA, direct HTTP calls for endpoint semantics, real Keycloak tokens for the auth matrix, and direct SQL to assert persisted state and provoke genuine lock conflicts. Bug-Fix then repairs the recorded failures at root cause in target code.

ProducesMG-01-Refactor-TestCase.md (191 cases, 13 categories) · MG-01-Refactor-TestResult.md with an overall scorecard
09

Security & code-quality gate /09-Quality-Security-Review

Security-ReviewCode-Quality-ReviewQuality-Security-Fix

Two reviewers run in parallel over the built code. Security-Review covers 15 domains — authn/authz, transport, injection, CSRF, secrets, PCI/GDPR data protection, dependency supply chain and more — and leads with a nine-metric scorecard. Code-Quality-Review covers 16 domains including layering conformance, transaction integrity, concurrency, accessibility, i18n and CI/CD gating, and first asks whether the client's own coding standard should be reviewed against. Neither touches code; Quality-Security-Fix is invoked separately, on confirmation, to remediate what they found.

ProducesMG-01-Security-Review.md · MG-01-CodeQuality-Review.md

Security review — 7 findings, grade F

  • Critical: no TLS anywhere in the built target — bearer tokens and all traffic travel in cleartext. This single finding forces the F.
  • High: JWT audience claim not enforced by default; any token from the same realm is accepted.
  • Authorization coverage 100% — all five endpoints guarded, matrix tested, no IDOR surface.
  • Injection resistance ~98% — parameterized queries throughout, no native SQL, no string concatenation.
  • Vulnerability density 1.9 per 1,000 LOC across 3,617 lines — an excellent band.

Code quality — 4 findings, grade B

  • High: the 1,138-line backend test suite has never been compiled or run, so mvn verify is unproven.
  • Architecture conformance 90% — clean controller→service→repository layering, DTOs only at the boundary.
  • Complexity ~4–6 average, duplication ~2%, issue density 2.2 per 1,000 LOC.
  • Open by design: no Tailwind, no schema-migration tooling, no CI/CD descriptor, no consolidated run guide.
  • Verified closed since the prior pass: concurrency lost-update, formatting gate, OpenAPI docs, logging, config hygiene, locale-aware messages.
