# MG-01.Architecture.md

## Architecture Overview
The Transaction Type Maintenance (MG-01) screen employs a modern, microservice-based architecture. The frontend is a React application providing a responsive and interactive user experience. It communicates with a backend service via stateless REST APIs. The backend is built using .NET Core 9 and ASP.NET Core Web API, responsible for enforcing business rules and ensuring data integrity. Data is persisted in a Postgres database. The system design emphasizes statelessness, security via OAuth 2.0 and TLS 1.3, and clear separation of concerns between presentation, domain logic, and data access.

## Component & Layer Definitions
- **Frontend (UI App)**: React SPA styled with Tailwind CSS. Handles routing, state management, presentation-layer validation, and UI microanimations.
- **API Gateway**: Serves as the entry point for frontend API calls. Handles request routing, CORS enforcement, and terminates TLS 1.3 connections.
- **Backend Service (API Layer)**: `.NET Core 9` ASP.NET Web API (`TransactionTypeService`). Contains REST controllers for routing endpoints (E1-E5) and services to execute domain logic.
- **Data-Access Layer**: Entity Framework Core or ADO.NET repository within the backend service. Translates domain operations into parameterized SQL queries against the database.
- **Database**: `Postgres` database hosting the `CARDDEMO` schema and the `TRANSACTION_TYPE` table for persistent storage of transaction types.

## Interaction / Data Flow
1. **User Action**: The user interacts with the React UI (e.g., clicking "Search" or "Save").
2. **API Request**: The frontend makes an HTTP request to the API Gateway over TLS 1.3, attaching the OAuth 2.0 JWT as a Bearer token.
3. **Routing & Auth**: The API Gateway routes the request to the `TransactionTypeService`. The service validates the JWT signature and required scopes (e.g., `TXN_TYPE_ADMIN`).
4. **Business Logic**: The service layer processes the request, applying business rules (e.g., checking for concurrent updates or required fields).
5. **Database Interaction**: The repository layer executes a parameterized SQL query (SELECT, INSERT, UPDATE, or DELETE) against the Postgres database.
6. **Response**: The database returns the result, which the service maps to a DTO (e.g., `TransactionTypeDto` or `ErrorResponseDto`) and sends back to the frontend as a JSON response.
7. **UI Update**: The frontend receives the response, updates the client-held state, and renders the success or error message to the user.

## Data Architecture
The data architecture relies on a single target table:
- **`CARDDEMO.TRANSACTION_TYPE`**: Stores the transaction type configuration. 
  - `TR_TYPE` (`CHAR(2)`): The Primary Key. 
  - `TR_DESCRIPTION` (`VARCHAR(50)`): The free-text description of the transaction type.
- This is reference data and does not contain any Personally Identifiable Information (PII). No other tables, VSAM files, or queues are accessed by this Tran Group. The schema is provisioned separately.

## Security & Compliance Architecture
- **Authentication & Authorization**: OAuth 2.0 with JWT. The backend acts as a Resource Server validating tokens. Administrative actions (Create, Update, Delete) require the `TXN_TYPE_ADMIN` scope.
- **Encryption in Transit**: HTTPS / TLS 1.3 is enforced at the API gateway and between the frontend and backend to protect data integrity and confidentiality.
- **OWASP Mitigation**: SQL injection is prevented by exclusively using parameterized queries via the data-access layer.
- **GDPR Compliance**: The data model manages only non-sensitive configuration codes. No PII is present, minimizing privacy risk by design.
- **Accessibility (WCAG 2.2 AA)**: The backend supports WCAG compliance by returning stable, machine-readable error codes (`TXN_TYPE_NOT_FOUND`, `DESCRIPTION_REQUIRED`, etc.) that the frontend maps to ARIA live regions for screen readers.

## Deployment/Topology (Logical)
- **Frontend App**: Deployed as static assets (HTML, JS, CSS) on a CDN or web server (e.g., NGINX, AWS S3/CloudFront).
- **API Gateway**: Deployed as an ingress controller or managed cloud API gateway (e.g., Kong, Azure API Management).
- **TransactionTypeService**: Deployed as a containerized application within a PaaS or orchestration platform (e.g., Kubernetes, Azure App Service).
- **Database**: Deployed as a managed relational database service (e.g., Amazon RDS for PostgreSQL, Azure Database for PostgreSQL).

## Open Architecture Decisions
- **None**: All technology choices (React, .NET Core 9, Postgres, OAuth 2.0, TLS 1.3) align precisely with the provided `Config/Config.md` constraints. No architectural deviations are required for this Tran Group.
