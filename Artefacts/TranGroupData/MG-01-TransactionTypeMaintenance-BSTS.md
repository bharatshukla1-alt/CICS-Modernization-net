# MG-01 — Transaction Type Maintenance (List, Add, Update, Delete)

## Group Membership

| Transaction | Program | Map / Mapset | Role in Group |
|---|---|---|---|
| CTLI | COTRTLIC | CTRTLIA / COTRTLI | Paged list/inquiry screen over `CARDDEMO.TRANSACTION_TYPE`, with inline row-select for Update or Delete, and PF2 hand-off to the add screen |
| CTTU | COTRTUPC | CTRTUPA / COTRTUP | Single-record search → view → edit/confirm/delete/add screen for one Transaction Type row |

Both programs are pseudo-conversational CICS/COBOL programs that read and maintain the DB2 table `CARDDEMO.TRANSACTION_TYPE` (key `TR_TYPE`, columns `TR_TYPE CHAR(2)` and `TR_DESCRIPTION VARCHAR(50)`, per `DCLTRTYP` in `Input/dcl/DCLTRTYP.dcl`). No VSAM files and no CICS TS queues are touched by either program.

---

## a. Business Summary

### Overall workflow

This group implements the maintenance of "Transaction Type" reference codes for the CardDemo application — the two-character codes (e.g. transaction category codes) and their free-text descriptions that other parts of the system presumably use to classify financial transactions. A business user (an administrator, based on the role flag set on entry — see below) reaches the list screen (CTLI/COTRTLIC), which shows up to seven Transaction Type rows at a time, optionally filtered by type code and/or a description search string, and lets the user either drill into a row for update/delete via inline row action codes, or jump to a dedicated add/update/delete screen (CTTU/COTRTUPC) to search for, review, change, delete, or create a specific Transaction Type by code. The two screens are cross-linked: the list screen's PF2 key hands off to the maintenance screen to add a brand-new code, and the maintenance screen's PF3 key returns either to the list screen or to whatever program originally invoked the workflow (falling back to the admin menu, program `COADM01C` / transaction `CA00`, if no caller is recorded).

### CTLI / COTRTLIC — List, filter, inline update/delete

The list screen exists to let the user browse existing Transaction Type codes and their descriptions, page forward and backward through the full set, and select records for correction or removal without leaving the list. On the screen, the user can supply a **Type Filter** (a specific 2-digit code) and/or a **Description Filter** (a partial-text search); leaving both blank returns the whole table in code order (Source: cursors `C-TR-TYPE-FORWARD`/`C-TR-TYPE-BACKWARD` in COTRTLIC, which apply the filters only when the corresponding edit flag is `'1'`, i.e. supplied).

Business rules enforced on those filters:
- The Type Filter, if supplied, must be exactly a 2-digit number; anything else is rejected with "TYPE CODE FILTER,IF SUPPLIED MUST BE A 2 DIGIT NUMBER" (Source: 1220-EDIT-TYPECD in COTRTLIC).
- The Description Filter, if supplied, is used as a "contains" search — the program wraps the trimmed text in `%...%` for a DB2 `LIKE` (Source: 1230-EDIT-DESC in COTRTLIC).
- If either filter is supplied but no rows in `CARDDEMO.TRANSACTION_TYPE` satisfy it (checked via a `SELECT COUNT(1)` before the page is fetched), the user is told "No Records found for these filter conditions" and the row-selection column is locked (protected) until the filter is corrected (Source: 9100-CHECK-FILTERS and 1290-CROSS-EDITS in COTRTLIC).

Each of the up to seven displayed rows carries a one-character action code the user can type: `U` to update that row's description in place, or `D` to mark it for deletion; any other non-blank value is rejected with "Action code selected is invalid" (Source: 1210-EDIT-ARRAY in COTRTLIC). Only one row may be actioned at a time — selecting `U` or `D` on more than one row at once produces "Please select only 1 action" and highlights every selected row in red (Source: 1210-EDIT-ARRAY in COTRTLIC, condition `WS-MORETHAN1ACTION`).

When a row is marked `U`, its description field becomes editable on the same screen; the new description is required (cannot be left blank) and may only contain letters, numbers, and spaces, enforced by the same alphanumeric-required edit used elsewhere in the group ("Transaction Desc must be supplied." / "...can have numbers or alphabets only.") (Source: 1211-EDIT-ARRAY-DESC and 1240-EDIT-ALPHANUM-REQD in COTRTLIC). If the user retypes the same description that was already on file (compared case-insensitively, trimmed), the system treats it as no real change and shows "No change detected with respect to database values." instead of proceeding to a save (Source: 1211-EDIT-ARRAY-DESC in COTRTLIC).

Both the Update and Delete paths follow a two-step "arm, then confirm" pattern: pressing Enter with a row marked `U` or `D` re-displays the list with a confirmation prompt — "Update HIGHLIGHTED row. Press F10 to save" or "Delete HIGHLIGHTED row ? Press F10 to confirm" — and the actual database change only happens when the user subsequently presses F10 (Source: main-line `EVALUATE` and 2500-SETUP-MESSAGE in COTRTLIC). As a safeguard, if the user changes the type filter, description filter, or which row is selected while a confirmation is pending and then presses F10, the system does not treat that F10 as a confirmation — it is silently converted back into a plain Enter/re-search, so a stale confirmation can never accidentally fire against a changed screen (Source: main-line `IF CCARD-AID-PFK10 ... AND FLG-TYPEFILTER-CHANGED-NO AND FLG-DESCFILTER-CHANGED-NO AND FLG-ROW-SELECTION-CHANGED-NO` in COTRTLIC).

On confirmed delete, the business outcome is "HIGHLIGHTED row deleted.Hit Enter to continue" and the screen resets to a fresh first-page search; if the row cannot be deleted because dependent/child data exists elsewhere in the database, the user instead sees "Please delete associated child records first:" (DB2 SQLCODE -532, a referential-constraint violation) (Source: 9300-DELETE-RECORD in COTRTLIC). On confirmed update, success shows "HIGHLIGHTED row was updated"; if the row was deleted by someone else in the meantime the message becomes "Record not found. Deleted by others ?", and a concurrent-update conflict (DB2 SQLCODE -911) is reported as "Deadlock. Someone else updating ?" (Source: 9200-UPDATE-RECORD in COTRTLIC).

Paging is cursor-driven and keyed on `TR_TYPE`: PF8 pages forward (fetching the next set of up to seven rows, with an extra "peek" fetch to know whether a further page exists), and PF7 pages backward to the previous set; paging past either end tells the user "No more pages to display" or "No previous pages to display" respectively (Source: 8000-READ-FORWARD, 8100-READ-BACKWARDS, 2500-SETUP-MESSAGE in COTRTLIC). If the very first search returns nothing at all, the message is instead "No records found for this search condition." (Source: 8000-READ-FORWARD, condition `WS-MESG-NO-RECORDS-FOUND`).

Exiting the list (PF3) returns control to whichever transaction/program invoked it (recorded in the shared commarea), defaulting to the Admin Menu if none is recorded (Source: main-line `IF CCARD-AID-PFK03` in COTRTLIC). Pressing PF2 instead hands off to the Transaction Type Update program (COTRTUPC/CTTU) so the user can add a brand-new code that isn't in the list (Source: main-line `IF CCARD-AID-PFK02` in COTRTLIC).

### CTTU / COTRTUPC — Search, view, update, delete, or add a single Transaction Type

This screen is a single-record workbench for one Transaction Type at a time. On entry, the user is prompted "Enter transaction type to be maintained" with just the 2-digit type-code field open for input (Source: 3250-SETUP-INFOMSG, `WHEN CDEMO-PGM-ENTER`, in COTRTUPC). The key itself is required, must be numeric, and must not be zero — enforced with "Tran Type code must be supplied.", "...must be numeric.", and "...must not be zero." respectively (Source: 1210-EDIT-TRANTYPE and 1245-EDIT-NUM-REQD in COTRTUPC).

Once a valid code is entered, the program looks the record up in `CARDDEMO.TRANSACTION_TYPE`:
- **Found** — the description is displayed and made editable, and the user is told "Update transaction type details shown." with Delete (F4) and Cancel (F12) available (Source: 9100-GET-TRANSACTION-TYPE and 3250/3391 setup paragraphs in COTRTUPC).
- **Not found** — the user is told "No record found for this key in database" and then, on the redisplay, prompted "Press F05 to add. F12 to cancel" (Source: 9100-GET-TRANSACTION-TYPE, 3250-SETUP-INFOMSG `WHEN TTUP-DETAILS-NOT-FOUND` in COTRTUPC).

**Update path**: with the record shown, the user edits the description in place and presses Enter. If the new description is identical to what was fetched (case-insensitive, trimmed comparison), the screen reports "No change detected with respect to values fetched." and nothing further happens (Source: 1205-COMPARE-OLD-NEW in COTRTUPC). If it genuinely differs and passes the same required/alphanumeric-only edit as the list screen, the user is asked to confirm: "Changes validated.Press F5 to save" (Source: 3250-SETUP-INFOMSG `WHEN TTUP-CHANGES-OK-NOT-CONFIRMED`). Pressing F5 commits the change; success is reported as "Changes committed to database" (Source: 9600-WRITE-PROCESSING, 3250-SETUP-INFOMSG `WHEN TTUP-CHANGES-OKAYED-AND-DONE`).

**Add path (business rule of note)**: if the key entered was not found, the user can press F5 to continue into "Enter new transaction type details." for that same code, then supply a description, confirm it ("Changes validated.Press F5 to save"), and press F5 to save. Functionally the save logic for "add" and "update" is the same paragraph: it first attempts a DB2 `UPDATE` of the description for that key, and only if that update affects zero rows (DB2 SQLCODE +100 — the key genuinely doesn't exist) does it fall through to an `INSERT` of the new row (Source: 9600-WRITE-PROCESSING and 9700-INSERT-RECORD in COTRTUPC). From the business user's perspective there is no visibly distinct "create" action — adding a new code and correcting an existing one are driven through the same confirm-and-save step.

**Delete path**: from the "found" state, F4 first asks "Delete this record ? Press F4 to confirm" — the same key must be pressed a second time to actually delete (Source: main-line `WHEN CCARD-AID-PFK04 AND TTUP-SHOW-DETAILS` then `WHEN CCARD-AID-PFK04 AND TTUP-CONFIRM-DELETE` in COTRTUPC). On confirmation, "Delete successful." is shown on success; if the row cannot be removed because dependent data exists, the message is "Please delete associated child records first:" with the SQLCODE and DB2 error text appended; any other database failure is reported as "Delete failed with message:" (Source: 9800-DELETE-PROCESSING in COTRTUPC).

**Cancel (F12)** behaves differently depending on where the user is in the flow: cancelling out of a pending delete confirmation reports "Delete was cancelled" and returns to the initial search-key prompt; cancelling out of a pending update confirmation reports "Update was cancelled" and instead falls back to re-displaying the originally fetched (unmodified) record, again inviting the user to update or cancel from there (Source: 2000-DECIDE-ACTION `WHEN CCARD-AID-PFK12` in COTRTUPC).

**Exit (F3)** always returns to whichever transaction/program the user came from, defaulting to the Admin Menu if none was recorded, exactly mirroring the list screen's exit behavior (Source: main-line `WHEN CCARD-AID-PFK03` in COTRTUPC).

A further entry-context business rule: arriving at this screen fresh (no data passed at all), or arriving from the Admin Menu, or arriving from the List screen (CTLI) without this being a mid-conversation re-entry, always discards any Transaction Type the user might have been partway through editing and forces the search-key prompt back to the start (Source: 0000-MAIN `IF EIBCALEN IS EQUAL TO 0 OR (CDEMO-FROM-PROGRAM = LIT-ADMINPGM AND NOT CDEMO-PGM-REENTER) OR (CDEMO-FROM-PROGRAM = LIT-LISTTPGM AND NOT CDEMO-PGM-REENTER)` in COTRTUPC).

### Business role note (uncertain downstream effect)

On entry, COTRTLIC marks the session as `CDEMO-USRTYP-ADMIN` (Source: 0000-MAIN in COTRTLIC), consistent with the list screen being an administrative function. However, when the user presses PF2 to jump to the add screen, the program explicitly switches the role flag to `CDEMO-USRTYP-USER` before handing off (Source: main-line `IF (CCARD-AID-PFK02 ...)` in COTRTLIC). Because the shared commarea copybook that defines `CDEMO-USRTYP-ADMIN`/`CDEMO-USRTYP-USER` (`COCOM01Y`) is not present in the supplied source (see Gaps), the business consequence of this role switch elsewhere in the wider CardDemo application cannot be confirmed from this group's source alone; it is recorded here as an observed, deliberate behavior rather than an assumption.

## b. Technical Summary

### COTRTLIC (CTLI)

**Entry and pseudo-conversational flow.** `0000-MAIN` initializes working storage and, on first invocation (`EIBCALEN = 0`), initializes the shared commarea (`CARDDEMO-COMMAREA`, copybook `COCOM01Y`) and sets `CDEMO-FROM-TRANID`/`CDEMO-FROM-PROGRAM` to this transaction/program, `CDEMO-USRTYP-ADMIN`, `CDEMO-PGM-ENTER`, and paging state `CA-FIRST-PAGE`/`CA-LAST-PAGE-NOT-SHOWN`; on re-entry it splits the inbound `DFHCOMMAREA` into the shared `CARDDEMO-COMMAREA` portion and a program-private area `WS-THIS-PROGCOMMAREA` (holding paging state, the last-fetched screen array, and delete/update-armed flags) (Source: 0000-MAIN in COTRTLIC). If control is returning from the Admin Menu (a different "from program") or the user pressed PF3 having come from the Add screen (CTTU), the program discards prior state and forces a fresh first-page entry (Source: 0000-MAIN, `IF (CDEMO-PGM-ENTER AND CDEMO-FROM-PROGRAM NOT EQUAL LIT-THISPGM) OR (CCARD-AID-PFK03 AND CDEMO-FROM-TRANID EQUAL LIT-ADDTTRANID)`). When re-entering from itself with data present, `1000-RECEIVE-MAP` (→ `1100-RECEIVE-SCREEN` → `1200-EDIT-INPUTS`) is performed to pull and validate the operator's input before any decision logic runs (Source: 0000-MAIN in COTRTLIC).

**PF-key handling.** `YYYY-STORE-PFKEY` (copybook `CSSTRPFY`, not present in supplied source — see Gaps) normalizes the raw AID byte into `CCARD-AID-*` condition names used throughout. The program only treats Enter, PF2, PF3, PF7, PF8, and PF10 (the latter only when a delete or update is armed) as valid; any other key is coerced back to Enter (Source: main-line `SET PFK-INVALID/PFK-VALID` logic in COTRTLIC). PF3 XCTLs to the caller (`CDEMO-TO-PROGRAM`/`CDEMO-TO-TRANID`, defaulting to `COADM01C`/`CA00`) after an `EXEC CICS SYNCPOINT`; PF2 XCTLs unconditionally to `COTRTUPC`, first setting `CCARD-NEXT-MAPSET`/`CCARD-NEXT-MAP` to `COTRTUP`/`CTRTUPA` and the role flag to `CDEMO-USRTYP-USER` (Source: main-line `IF CCARD-AID-PFK03` / `IF CCARD-AID-PFK02` in COTRTLIC). In both XCTL cases, `CARDDEMO-COMMAREA` is the only data passed (the program-private `WS-THIS-PROGCOMMAREA` is not forwarded across the XCTL).

**Map I/O.** `1100-RECEIVE-SCREEN` issues `EXEC CICS RECEIVE MAP('CTRTLIA') MAPSET('COTRTLI') INTO(CTRTLIAI) RESP(WS-RESP-CD)`, then unloads the type/description filters and the seven-row select/type/description array from the symbolic map (Source: 1100-RECEIVE-SCREEN in COTRTLIC). Output is built across `2100`–`2500` (screen header/date/time, per-row attribute setup including protect/color/cursor placement in `2200-SETUP-ARRAY-ATTRIBS`, row data population in `2300-SCREEN-ARRAY-INIT`, filter-field attributes in `2400-SETUP-SCREEN-ATTRS`, and message construction/centering in `2500-SETUP-MESSAGE`) and sent by `2600-SEND-SCREEN` via `EXEC CICS SEND MAP('CTRTLIA') MAPSET('COTRTLI') FROM(CTRTLIAO) CURSOR ERASE RESP(WS-RESP-CD) FREEKB`. There is no explicit `MAPFAIL` handling; the RESP code from the receive is captured into `WS-RESP-CD` but not branched on beyond the standard flow.

**Data access.** All data access is DB2, via two named forward/backward scrolling cursors declared against `CARDDEMO.TRANSACTION_TYPE`: `C-TR-TYPE-FORWARD` (`WHERE TR_TYPE >= :WS-START-KEY ... ORDER BY TR_TYPE`) and `C-TR-TYPE-BACKWARD` (`WHERE TR_TYPE < :WS-START-KEY ... ORDER BY TR_TYPE DESC`), both conditionally applying the type/description filters (Source: cursor `DECLARE`s in the WORKING-STORAGE SECTION of COTRTLIC). `8000-READ-FORWARD` opens/fetches/closes `C-TR-TYPE-FORWARD` in a loop bounded by `WS-MAX-SCREEN-LINES` (7), with an extra fetch beyond the seventh row purely to detect whether a further page exists (`CA-NEXT-PAGE-EXISTS`/`CA-NEXT-PAGE-NOT-EXISTS`); `8100-READ-BACKWARDS` does the symmetric fetch for Page-Up via `C-TR-TYPE-BACKWARD`. `9100-CHECK-FILTERS` issues a `SELECT COUNT(1)` against the same table/filter predicate to short-circuit an empty result before paging. `9200-UPDATE-RECORD` performs `UPDATE CARDDEMO.TRANSACTION_TYPE SET TR_DESCRIPTION = :DCL-TR-DESCRIPTION WHERE TR_TYPE = :DCL-TR-TYPE`, and `9300-DELETE-RECORD` performs `DELETE FROM CARDDEMO.TRANSACTION_TYPE WHERE TR_TYPE = :DCL-TR-TYPE`; both are followed by `EXEC CICS SYNCPOINT` on success (Source: 9200-UPDATE-RECORD, 9300-DELETE-RECORD in COTRTLIC).

**Exception handling.** DB2 connectivity is verified once per invocation via `9998-PRIMING-QUERY` (copybook `CSDB2RPY`), issuing `SELECT 1 FROM SYSIBM.SYSDUMMY1 FETCH FIRST 1 ROW ONLY`; any non-zero `SQLCODE` sets `WS-DB2-ERROR`, formats a diagnostic message via `9999-FORMAT-DB2-MESSAGE` (which calls the `DSNTIAC` DB2 utility to expand the SQLCODE into text, copybook `CSDB2RWY` for the associated working storage), and the transaction terminates early through `SEND-LONG-TEXT`/`SEND-LONG-TEXT-EXIT` rather than attempting any data operation (Source: 0000-MAIN, 9998-PRIMING-QUERY in CSDB2RPY, 9999-FORMAT-DB2-MESSAGE in CSDB2RPY). Each individual cursor `OPEN`/`FETCH`/`CLOSE` and each `UPDATE`/`DELETE` explicitly evaluates `SQLCODE` (0, +100, -911, -532, and other negative codes handled distinctly) rather than relying on a blanket `HANDLE CONDITION`; there is no `EXEC CICS HANDLE ABEND` in this program.

### COTRTUPC (CTTU)

**Entry and pseudo-conversational flow.** `0000-MAIN` begins by registering `EXEC CICS HANDLE ABEND LABEL(ABEND-ROUTINE)` before any other processing (Source: 0000-MAIN in COTRTUPC). On `EIBCALEN = 0`, or when the caller was the Admin Menu or the List program and this is not a pseudo-conversational re-entry (`NOT CDEMO-PGM-REENTER`), the program re-initializes the shared and private commareas and forces `TTUP-DETAILS-NOT-FETCHED`; otherwise it splits the inbound `DFHCOMMAREA` exactly as COTRTLIC does, into `CARDDEMO-COMMAREA` and the private `WS-THIS-PROGCOMMAREA` (which carries a state byte `TTUP-CHANGE-ACTION` driving a small state machine — not-fetched/invalid-keys/not-found/show-details/create-new/review-new/delete-in-progress sub-states/changes-made sub-states/changes-failed sub-states/changes-done/changes-backed-out — plus old and new copies of the type/description fields) (Source: 0000-MAIN and the 88-level state definitions under `TTUP-CHANGE-ACTION` in COTRTUPC).

**PF-key handling.** `YYYY-STORE-PFKEY` (copybook `CSSTRPFY`) is invoked identically to COTRTLIC, then `0001-CHECK-PFKEYS` re-validates the AID against the current state — PF3 always valid; Enter valid unless a delete confirmation is pending; PF4 valid only from show-details or confirm-delete; PF5 valid only from a pending confirmed-change, not-found, or an in-progress delete state; PF12 valid only from a pending confirmed-change, show-details, not-found, or confirm-delete state — any other combination sets `WS-INVALID-KEY-PRESSED` ("Invalid key pressed") (Source: 0001-CHECK-PFKEYS in COTRTUPC). The screen's `FKEY06` ("F6=Add") map field is defined with `ATTRB=DRK` (dark/non-display) in the BMS source and is never turned bright by `3391-SETUP-PFKEY-ATTRS`, and no `CCARD-AID-PFK06` condition is ever tested in the procedure division — F6 is a vestigial/inactive key in this program (Source: BMS `FKEY06` field in COTRTUP.bms; absence of any PFK06 handling in COTRTUPC). Similarly the 88-levels `FOUND-TRANTYPE-DATA` and `CODING-TO-BE-DONE` under `WS-INFO-MSG` are declared but never `SET` anywhere in the program.

**XCTL transitions.** PF3 XCTLs to `CDEMO-TO-PROGRAM` (from `CDEMO-FROM-PROGRAM`, defaulting to `COADM01C`/`CA00`) passing only `CARDDEMO-COMMAREA`, preceded by `EXEC CICS SYNCPOINT`, mirroring COTRTLIC exactly (Source: main-line `WHEN CCARD-AID-PFK03` in COTRTUPC). There is no XCTL back to COTRTLIC from this program in the source examined; the List program is only referenced as a possible `CDEMO-FROM-PROGRAM` value used to decide whether to reset state (`LIT-LISTTPGM` = `COTRTLIC`).

**Map send/receive sequencing.** `1100-RECEIVE-MAP` issues `EXEC CICS RECEIVE MAP('CTRTUPA') MAPSET('COTRTUP') INTO(CTRTUPAI) RESP(WS-RESP-CD) RESP2(WS-REAS-CD)` (this program, unlike COTRTLIC, also captures `RESP2`) (Source: 1100-RECEIVE-MAP in COTRTUPC). `1150-STORE-MAP-IN-NEW` copies the symbolic map's `TRTYPCDI`/`TRTYDSCI` fields into the private "new" data area, treating `'*'` or spaces as low-values (cleared), unless the details-not-found state is unchanged from the last pass (in which case the stored key is left alone to avoid re-triggering an unnecessary re-edit). Output is assembled by `3100`–`3391` (header/date-time, screen-variable population branching on the current `TTUP-*` state in `3200-SETUP-SCREEN-VARS`/`3201`–`3203`, info-message selection in `3250-SETUP-INFOMSG`, field protection/highlighting in `3300-SETUP-SCREEN-ATTRS`/`3310`/`3320` including a `COPY CSSETATY REPLACING` for the description field's status attributes, info-message brightness in `3390-SETUP-INFOMSG-ATTRS`, and PF-key legend visibility in `3391-SETUP-PFKEY-ATTRS`) and sent by `3400-SEND-SCREEN` via `EXEC CICS SEND MAP(CCARD-NEXT-MAP) MAPSET(CCARD-NEXT-MAPSET) FROM(CTRTUPAO) CURSOR ERASE FREEKB RESP(WS-RESP-CD)`. No explicit `MAPFAIL` branch is coded.

**Data access.** All data access is DB2 against `CARDDEMO.TRANSACTION_TYPE` (declared via `DCLTRTYP`); the program also `EXEC SQL INCLUDE`s `DCLTRCAT` (the `TRANSACTION_TYPE_CATEGORY` declaration) but no SQL statement in this program's procedure division references `DCL-TRC-*` or that table — the include is present but unused by any logic seen in source (Source: absence of `TRC_`/`DCL-TRC` references in COTRTUPC's PROCEDURE DIVISION). `9100-GET-TRANSACTION-TYPE` performs `SELECT TR_TYPE, TR_DESCRIPTION ... WHERE TR_TYPE = :DCL-TR-TYPE` (Read), setting `FOUND-TRANTYPE-IN-TABLE` on `SQLCODE = 0` and `FLG-TRANFILTER-NOT-OK`/"No record found..." on `+100`, or a formatted "Error accessing:...SQLCODE:...:SQLERRM" message on any negative code. `9600-WRITE-PROCESSING` issues `UPDATE CARDDEMO.TRANSACTION_TYPE SET TR_DESCRIPTION = :DCL-TR-DESCRIPTION WHERE TR_TYPE = :DCL-TR-TYPE` (Update); on `SQLCODE = 0` it syncpoints; on `+100` (no row updated) it falls through to `9700-INSERT-RECORD`, which performs `INSERT INTO CARDDEMO.TRANSACTION_TYPE (TR_TYPE, TR_DESCRIPTION) VALUES (...)` (Create) and syncpoints on success; `SQLCODE = -911` and other negative codes on the update are distinguished into lock-error vs. generic-update-failure outcomes. `9800-DELETE-PROCESSING` issues `DELETE FROM CARDDEMO.TRANSACTION_TYPE WHERE TR_TYPE = :DCL-TR-TYPE` (Delete), syncpointing on success and distinguishing `SQLCODE = -532` (child-record/referential-constraint failure) from other delete failures (Source: 9100-GET-TRANSACTION-TYPE, 9600-WRITE-PROCESSING, 9700-INSERT-RECORD, 9800-DELETE-PROCESSING in COTRTUPC).

**Exception/integrity handling.** Unlike COTRTLIC, this program registers `EXEC CICS HANDLE ABEND LABEL(ABEND-ROUTINE)` up front. The `2000-DECIDE-ACTION` state-transition `EVALUATE` ends in a catch-all `WHEN OTHER` that treats any state combination it does not recognize as a programming/data integrity fault: it moves `'0001'` into `ABEND-CODE`, `'UNEXPECTED DATA SCENARIO'` into `ABEND-MSG`, and performs `ABEND-ROUTINE`, which sends the formatted abend diagnostic data (`ABEND-DATA`, copybook `CSMSG02Y`) to the terminal with `NOHANDLE`, cancels the abend handler (`EXEC CICS HANDLE ABEND CANCEL`), and issues `EXEC CICS ABEND ABCODE('9999')` (Source: 2000-DECIDE-ACTION `WHEN OTHER`, ABEND-ROUTINE in COTRTUPC). All DB2 calls check `SQLCODE` explicitly rather than using `EXEC SQL WHENEVER`.
