Is the target actually microservices?

It is one correctly-built microservice — not a microservices architecture.

Every structural property of a microservice holds inside the one service that exists. None of the properties that only appear between services can be observed, because there is exactly one. The pattern is right; the system is N = 1, so the label in Config/Config.md and the HTML report is aspirational rather than demonstrated.

The distinction that matters

A microservice is a shape. Microservices is a topology.

Reviewing Target/MG-01/ answers two different questions, and the report currently conflates them. The first — is this service shaped like a microservice? — is about bounded context, statelessness, data ownership, and independent deployability. It passes cleanly. The second — is this a microservices system? — is about decomposition, an edge, and service-to-service communication. There is nothing yet to decompose into, no gateway in front, and no peer to talk to.

What is missing — and why you could not have known

Artefacts/Architecture/MG-01.Architecture.md describes components that do not exist in Target/. Each row quotes the architecture document, then states what the code does.

Status Component Document claim vs. built reality
Absent API gateway “…talks over REST (through an API gateway)… The API gateway terminates TLS, validates the bearer token at the edge, and forwards to the service.” No gateway exists anywhere in the repository. The SPA reaches Spring directly through the Vite dev proxy — vite.config.js forwards /api to http://localhost:8080.
Absent TLS 1.3 transport “TLS 1.3 — terminated at the API gateway/ingress; HTTP rejected, HSTS set.” The service listens on plain HTTP. There is no server.ssl.* block in application.yml and no ingress to terminate at. .Claude/settings.local.json still allowlists https://localhost:8443, an endpoint nothing serves.
Absent A second service “Style… A single-purpose, service-based / microservice deployment.” Accurate as written — and that is the point. One service cannot be independent of anything. Only Target/MG-01/ exists; there is no MG-02.
N/A at N=1 Discovery, resilience, messaging A grep across src/main/java for RestTemplate, WebClient, FeignClient, EnableDiscoveryClient, CircuitBreaker, KafkaTemplate and RedisTemplate returns nothing. Legitimately so — MG-01 uses no VSAM, TSQ, TDQ or MQ, so there is genuinely nothing to call.
Absent Deployment unit No Dockerfile, compose file, Helm chart or Kubernetes manifest under Target/. Independent deployability is therefore a design claim that has never been exercised. The only Dockerfile in the repository belongs to the vendored mcp-database-server.

The specified path and the built path

Corroboration

The code already documents both gaps

These are not inferences. The build files state the absence in their own comments — which is why the remediation was pushed into the service in the first place.

pom.xml · bucket4j dependency

“SEC-006: token-bucket rate limiting applied in-process (no API gateway exists in the built target). Used by RateLimitFilter.”

Rate limiting belongs at the edge. It sits inside the service precisely because there is no edge — and the buckets are in-memory, so the budget is per instance and would not survive horizontal scaling.

application.yml · app.security.expected-audiences

“Set JWT_EXPECTED_AUDIENCES to the audience value the Keycloak client actually mints — required before a second microservice shares this realm. Empty keeps issuer/signature/expiry-only validation.”

The value is empty today, so the aud claim is not enforced. The comment is explicit that this is safe only while the realm has a single consumer.

application.yml · datasource url

“Keep prefer for a local sandbox Postgres that has no server certificate, and set require … for every shared or deployed environment.”

Configured as DB_SSL_MODE:prefer. The knob exists and is correctly placed; it has simply never been turned, because there is no deployed topology to turn it for.

Repeatable check

How to answer this yourself, for any group

Run these four from the repository root against any Target/<Group>/. Together they separate “a microservice” from “microservices” without reading a line of the architecture document.

How many independently deployable units are there? 
find Target -name pom.xml \
  -not -path "*/target/*" | wc -l
1 Microservices requires more than one. One is a service.
Does each service exclusively own its tables? 
grep -rn "@Table" \
  Target/*/Backend/*/src/main/java
transaction_type — once The same table mapped in two services means a shared database, which disqualifies the topology.
Is there an edge — gateway, ingress, or TLS? 
grep -rn "server.ssl\|gateway\|ingress" \
  Target/ --include=*.yml --include=*.xml
no matches No edge means TLS termination and edge authentication are unowned, whatever the document says.
Is the service actually shippable on its own? 
find Target -iname "Dockerfile*" \
  -o -iname "docker-compose*"
no matches Without a deployment unit, independent deployability has never been tested.
Recommendation

Wording that survives review

Currently Architecture Type: Microservices Replace with Service-based architecture — one stateless, independently deployable service owning its bounded context. Gateway, TLS termination, and containerization are specified but not yet built.
Becomes “microservices” when: MG-02 ships as a second service, behind a real gateway, with JWT_EXPECTED_AUDIENCES set and DB_SSL_MODE=require. Building the gateway before that second service buys nothing — the in-process rate limiter and the direct proxy are the correct call at N = 1.
